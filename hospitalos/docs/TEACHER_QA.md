# Questions My Teacher May Ask (with simple answers)

**1. What is MCP?**
Model Context Protocol — an open standard that lets an AI call tools in a uniform way. Each MCP server
offers tools (with names, descriptions and input schemas); any MCP client can discover and call them.
Think of it as "USB for AI tools".

**2. Why not just let the AI read the database directly?**
Tools give control: each one validates input, returns only what's needed, and is labelled READ or WRITE.
The AI can't run arbitrary changes. (The ready-made database connector is limited to read-only tools.)

**3. How does the AI know which tool to use?**
We send the LLM every tool's name, docstring and parameters. The docstrings say when to use the tool
("Use this when staff ask how many free beds…"). The LLM picks the tool and fills the arguments.

**4. What stops the AI from changing data by mistake?**
Code, not just the prompt. When the LLM asks for a WRITE tool, the agent pauses and returns a confirmation
request. The tool runs only after the user clicks Yes, using a one-time id that expires in 10 minutes.

**5. What if the AI makes up an answer?**
The system prompt forbids answering from memory and the UI shows every tool call with its input and output,
so answers can be checked. When a tool finds nothing, the AI is told to say so — tested in our test suite.

**6. Which LLM do you use? Is it paid?**
Any OpenAI-compatible API. We use the Gemini free tier or Groq free tier. Switching needs only three values
in `.env`: LLM_BASE_URL, LLM_API_KEY, LLM_MODEL. No billing is needed.

**7. Is the patient data real?**
No. All data is generated by `data/seed.py` with the Faker library. Phone numbers use the fake 555 prefix.

**8. Why so many separate MCP servers instead of one?**
Separation of concerns: each team member owns one server; one crashing doesn't break the others;
it mirrors real hospitals where departments run separate systems.

**9. What is the tool-calling loop?**
Ask LLM → LLM requests tools → we run them → send results back → repeat until the LLM gives a final answer.
We cap it at 6 rounds so it can never loop forever.

**10. How do the AI agent and MCP servers talk?**
Over stdio: the hub starts each server as a child process and exchanges JSON-RPC messages through
its standard input/output, using the official MCP Python SDK.

**11. What happens if a server or the LLM fails?**
A server that won't start is marked "failed" (visible on the Settings page) and the rest keep working.
LLM rate limits are retried up to 3 times, then the user gets a friendly message. Tool errors are passed
to the AI as text so it can explain them.

**12. How did you test it?**
46 pytest tests: every MCP tool (success, not found, bad input), the API, and three agent scenarios
(read question, write with confirmation yes/no, failures) using real MCP servers with a scripted fake LLM,
all on a temporary copy of the database.

**13. Can it use PostgreSQL?**
Yes. Change `DATABASE_URL` in `.env` to a PostgreSQL URL (and install the `psycopg2-binary` driver).
SQLAlchemy handles the rest.

**14. What are the ready-made MCP servers?**
`@modelcontextprotocol/server-filesystem` (official reference server, restricted to the `reports/` folder)
and `mcp-server-sqlite` (reference SQLite server, read-only tools only). We also wrote a small custom
openFDA server for public drug information.

**15. What is FastAPI / React / Tailwind doing here?**
FastAPI = the backend web API (and auto-generated docs at /docs). React = the user interface.
Tailwind = CSS utility classes; our colours, fonts and radii are defined once in `tailwind.config.js`.

**16. What are the limitations?**
Free-tier rate limits, no login/roles yet, synthetic data only, English only.

**17. What would you add next?**
Role-based login, an audit log of every write, voice input, FHIR export, Docker deployment.
